# 説明文（メモ）の付与

説明が無い / 簡素な定義を検出し、実際の処理内容にもとづく説明文を生成して `description` に付与する。

## 大原則: API はラッパー `trocco-api.sh` 経由で呼ぶ

`curl` で直接叩かない。ベース URL と `Authorization` ヘッダーはラッパーが所有するので、
**パス以降と curl 引数だけ**を渡す（API キーの値を読む必要はない）。

ラッパーの置き場所は導入方法によって変わる。まず次でパスを確定する。

```bash
# ls はエイリアス（-F 等）で表示が変わることがあるため使わない
for p in {.claude,.agents}/skills/govern-descriptions/scripts/trocco-api.sh bin/trocco-api.sh; do
  [ -f "$p" ] && echo "$p" && break
done
```

以降この SKILL.md と `references/` に出てくる `trocco-api.sh` は、確定したパスに読み替えて実行する。
コマンドごとにシェルは切り替わるため、変数には入れず毎回フルパスで書く。

```bash
bash .claude/skills/govern-descriptions/scripts/trocco-api.sh "/job_definitions?limit=200"   # パスは確定した値に置き換える
```

## 前提知識（必ず先に読む）
- [`knowledge/trocco-api.md`](./references/trocco-api.md)
- [`knowledge/descriptions.md`](./references/descriptions.md): 検出方法・生成の材料と方針

## 手順

### 1. 対象の洗い出し（読み取りのみ）
対象種別を確認し、`description` が null / 空 / 極端に短い定義を列挙する。

**「空」と「短いが書かれている」は分けて提示する**（対応方針が違うため）:

```
説明なし（空）: A 件      ← 新規生成。上書きの懸念が無いので優先
説明が短い: B 件          ← 既存の意図を尊重し、補強案として提示
```

**閾値の既定は「空」＋「10 文字未満」**とする。日本語は情報密度が高く、
`サンプルデータマート定義`（12 文字）のように短くても意味が通る説明があるため、
英語想定の 20 文字では過剰に拾ってしまう（実測で確認）。閾値は実行時にユーザーへ確認し変更可能にする。

> [!NOTE]
> **レートリミットに注意**（10 分あたり トライアル 100 回 / Advanced 以上 3,500 回）。
> この skill は対象 1 件につき detail を 1 回取得するため、対象が多いと上限に近づく。
> **実行前に必要回数を見積もり**（一覧 ≒ 全件÷200 回 ＋ detail ≒ 対象件数）、
> 上限に対して大きい場合は対象を絞るかユーザーに確認する。
> ラッパーは 429 を自動リトライする。残量確認:
> `trocco-api.sh '/teams?limit=1' -o /dev/null -D - 2>/dev/null | grep -i x-rate-limit`

### 2. 処理内容の把握
各定義を GET し、実際の設定から処理内容を読み取る:
- 転送設定: 転送元/先コネクタ・テーブル/クエリ・書き込み mode・フィルタ・差分/洗い替え・スケジュール
- データマート: 実行 SQL の要約・出力先・write_disposition・スケジュール
- ワークフロー: tasks の種別と参照先・依存の流れ・スケジュール

### 3. 説明文の生成（事実ベース）
- 「入力 → 処理 → 出力 → 頻度」の順で 1〜3 文にまとめる。
- 設定に書かれた事実のみ。SQL の意図を過剰に推測しない。
- **PII / 認証値 / 社外秘の情報を説明文に転記しない**。

### 4. 確認して適用
- 生成した説明文をユーザーに提示（既存の簡素な説明を上書きする場合は before/after）。
- 承認後、`description` のみを PATCH（スカラーなので他設定は保持される）。
- まず数件で品質を確認 → 横展開。変更した id 一覧を報告。

## やってはいけないこと
- 設定に無い内容を推測で書かない。
- 既存の説明を無断で上書きしない。
- 個人情報・秘匿情報を説明文に含めない。
