# ジョブの実行ログを読み、失敗原因を説明する

ジョブを 1 つ受け取り、実行結果と実行ログを API で取得して、何が起きたか・なぜ失敗したか・どう直すかを報告する。
読み取りのみで、設定の変更やジョブの再実行はしない。

## 大原則: 生の実行ログを AI の入力に入れない

実行ログと定義には、接続先のホスト名・ユーザー名・ファイルパス・クエリ・データの値が含まれうる。
**これらは伏せ字にしてから読む**。生のログを読み、あとから報告で伏せるのでは遅い（読んだ時点で AI の入力に入っている）。

- 取得は必ず同梱の `scripts/fetch-job-logs.sh` で行う。生データは作業ディレクトリの `.raw/` に保存され、
  伏せ字にしたもの（`log.txt` / `error_log.txt` / `definition.json` など）だけが作業ディレクトリ直下に置かれる。
- **`.raw/` の中身を `cat` / `grep` / `sed` / `head` / `tail` / `jq` などで直接読まない**。
  ログや定義の取得 API（`/logs`、定義の詳細）を `trocco-api.sh` で直接叩いて画面に出すこともしない。
- 伏せ字は**許可リスト方式**: どの顧客でも同じになる文字列（エラー文の一般的な英単語、SQL / HTTP の用語、
  Java の例外クラス名、エラーコードらしい形、5 桁以下の数字、カスタム変数のプレースホルダー）だけが残り、
  それ以外は `‹…›` になる。原因の特定はまずこれだけで行う。
- 伏せ字のせいで判断できないときに限り、**ユーザーの許可を得て**、必要な行範囲だけを `redact.sh mask` で見る（下記手順 4）。
  マスキング方式はホスト名・URL・メール・IP・パス・認証情報らしい値・長い ID を伏せるが、
  **テーブル名・列名・引用符内の語などは残る**。許可を求めるときにそう伝える。

## 大原則: API はラッパー `trocco-api.sh` 経由で呼ぶ

`curl` で直接叩かない。ベース URL と `Authorization` ヘッダーはラッパーが所有するので、
**パス以降と curl 引数だけ**を渡す（API キーの値を読む必要はない）。

ラッパーの置き場所は導入方法によって変わる。まず次でパスを確定する。

```bash
# ls はエイリアス（-F 等）で表示が変わることがあるため使わない
for p in {.claude,.agents}/skills/troubleshoot-job-logs/scripts/trocco-api.sh bin/trocco-api.sh; do
  [ -f "$p" ] && echo "$p" && break
done
```

以降この SKILL.md と `references/` に出てくる `trocco-api.sh` は、確定したパスに読み替えて実行する。
同じ `scripts/` に `fetch-job-logs.sh` と `redact.sh` がある（リポジトリの `bin/` には無いので、
`bin/trocco-api.sh` に確定した場合は `.apm/skills/troubleshoot-job-logs/scripts/` のものを使う）。
コマンドごとにシェルは切り替わるため、変数には入れず毎回フルパスで書く。

```bash
bash .claude/skills/troubleshoot-job-logs/scripts/trocco-api.sh "/jobs/123"   # パスは確定した値に置き換える
```

## 手順

### 1. 対象ジョブの種別と ID を確定する

引数（無ければユーザーに尋ねる）から、ジョブの種別と ID を決める。

| 入力 | 種別 | 実行結果 | 実行ログ |
|---|---|---|---|
| `https://trocco.io/jobs/<id>` | 転送 | `/jobs/<id>` | `/jobs/<id>/logs` |
| `https://trocco.io/datamart/jobs/<id>` | データマート | `/datamart_jobs/<id>` | `/datamart_jobs/<id>/logs` |
| `https://trocco.io/dbt_jobs/<id>` | dbt | `/dbt_jobs/<id>` | `/dbt_jobs/<id>/logs` |
| `https://trocco.io/pipeline_jobs/<id>` | ワークフロー | `/pipeline_jobs/<id>` | なし（下記） |
| `datamart:<id>` / `dbt:<id>` | 指定どおり | | |
| 数字だけ | 転送とみなす | | |

- 数字だけのときは「転送ジョブとして調べる」と一言添えて進める。
- **転送ジョブで 404 が返っても、データマートや dbt の同じ ID を勝手に試さない**。ジョブ ID は種別ごとに
  別の採番で、無関係なジョブのログを読んでしまう。種別を確認するか URL を貰う。
- **ワークフロージョブの ID / URL を渡されたとき、または「ワークフローが落ちた」と依頼されたとき**は、
  `job-logs.md`「ワークフロージョブが失敗したとき」に従う。要点:
  1. `/pipeline_jobs/<id>` でステータスと時刻だけを示す。
  2. **API ではどのタスクが失敗したかも、タスクの結果も分からない**ことを伝え、
     **実際に失敗しているタスクのジョブ ID（できればジョブ画面の URL）**を依頼する。
     ワークフロージョブの詳細画面で失敗したタスクを開くと、そのジョブの画面に移れる、と案内する。
  3. そのタスクが**転送ジョブ・データマートジョブ（dbt ジョブも同様）ならログを取得できる**ので、
     受け取った ID / URL で手順 2 以降を行う。子ワークフローなら同じ手順を繰り返し、
     それ以外のタスク（データチェック・HTTP リクエスト等）は画面で確認してもらう。
  ユーザーがジョブ ID を用意できないときだけ、同節の補助手段（転送タスクの推定）を、推定である旨を添えて使う。

### 2. 伏せ字にして読むことをユーザーに伝える

取得の前に、次を一言で伝える。

- 実行ログと定義の詳細を取得し、**伏せ字にしたものだけを読む**こと（ホスト名・ユーザー名・データの値などは読まない）
- 伏せ字で判断できないときは、見たい行範囲と理由を示して、改めて許可を求めること

### 3. 実行結果・実行ログ・定義を取得する

```bash
bash <scripts>/fetch-job-logs.sh jobs <id>            # 転送。データマートは datamart_jobs、dbt は dbt_jobs
```

標準出力に、伏せ字済みの実行結果の要約・ログのストリームの状態・読んでよいファイルの一覧が出る。
作業ディレクトリは既定で `${TMPDIR:-/tmp}/trocco_troubleshoot_<種別>_<id>`（以下 `$out`）。

- 要約には定義名・メモ・実行クエリを出さない（利用者が自由に書く文字列のため）。報告ではジョブ URL を主語にする。
- `succeeded` のときは「成功している」と伝えたうえで、警告やスキップ行（`skipped_row_count`）など
  ユーザーが気にしていそうな点をログから確認する。ユーザーが成功ジョブの何を知りたいのか不明なら尋ねる。
- `queued` / `setting_up` / `executing` のときは、ログは取得時点までのものになる（`pending` のこともある）。
  その旨を伝え、今読むか完了を待つかをユーザーに確認する。
- ログ取得が 503 のときは `Retry-After` の秒数だけ待って 1 回だけ再実行する。続けて失敗したら時間を置くよう伝える。
- ストリームの `status` が `expired`（約 1 年経過）なら取得できない。実行結果だけで報告する。
- `truncated` が `true` なら、中間が省略されていることを報告に必ず添える。

### 4. 原因箇所を特定する

伏せ字済みのファイル（`$out/log.txt` / `$out/error_log.txt`）だけを読む。各行の先頭に元のログの行番号が付いている。
ログ全文を一度に読まない。`job-logs.md`「どこに原因が書かれているか」に従い、根本原因の行を探して前後を読む。
転送ジョブは `log` と `error_log` の**両方**を探す（どちらに出るかは決まっていない。`error_log` には無害な警告も `[ERROR]` 付きで大量に出る）。

```bash
wc -l "$out"/*.txt
grep -E 'Caused by:|\]: Error:|Exception:' "$out"/log.txt "$out"/error_log.txt | cut -c1-400 | tail -20
tail -n 40 "$out/log.txt"
```

- 例外の連鎖は**最後の `Caused by:`** まで追う。外側の例外名だけで結論を出さない。
- 伏せ字（`‹…›`）の中身が判断に必要なとき（例: どの列・どのパラメータが原因か）は、**行番号と理由を示してユーザーに許可を求め**、
  許可された範囲だけを見る。一度に 200 行まで。範囲は必要最小限にする。

  ```bash
  bash <scripts>/redact.sh mask "$out/.raw/log.txt" <開始行> <終了行>
  ```

- 転送ジョブは `/job_definitions/<定義ID>/jobs` で実行履歴を確認し、**最初に失敗したジョブ**と**最後に成功したジョブ**を押さえる
  （1 回 100 件まで・新しい順。`job-search.md` 参照）。実行履歴にはログや設定の値は含まれないので、`trocco-api.sh` で直接取ってよい。
  散発か、ある時点から毎回か、作成以来一度も成功していないかで打ち手が変わる。データマート・dbt には一覧 API が無い。

### 5. 定義の現況を突き合わせる

`job-definition-context.md` に従い、手順 3 で取得した**伏せ字済みの定義**（`$out/definition.json`）を、ログのエラーと突き合わせる。
**修正を提案するときは必ず行う**（ログだけで設定変更の中身を推測しない）。

- 見る項目: 書き込みモード（再実行してよいか）、クエリ・取得対象の形（`SELECT *` か、カスタム変数のプレースホルダーか）、
  列定義の数、カスタム変数、作成・更新日時（一覧 API から）
- 書き込みモードなどの列挙値はそのまま残り、認証情報らしい項目は常に `‹secret›` になる
- 具体的な値（クエリの全文、列名など）が要るときは、手順 4 と同じく許可を得て `redact.sh mask "$out/.raw/definition.json" <開始行> <終了行>` で見る
- 現在の設定であって実行時点の設定ではない。定義の更新が失敗より後なら、その旨を添える
- 定義の詳細を取得できなかった（転送設定の一部コネクタは 400 で未サポート）ときは、ログと一覧の情報だけで判断する

### 6. ヘルプセンターと障害報告を確認する

`help-center-search.md` に従い、**その場で**検索する（記事の内容を記憶や過去の結果で補わない）。

- 手順 4 で特定したエラーから、例外クラス名・エラーコードなどの短いトークンを取り出して検索する。
  検索語は**伏せ字済みのファイルに残っている語から**選ぶ（許可を得て見た値は検索語に使わない）。
  ヒットしなければコネクタ名＋症状の日本語で探し直す。**検索語にログ中の値（ホスト名・テーブル名・データ）を入れない**。
- ヒットした記事は、コネクタ・向き・エラー文字列・発生場面がログと一致するかを確かめてから使う。
  一致しなければ採用しない。記事が無くても、ログから判断する。
- 「設定を変えていないのに落ちた」ときは、失敗時刻（転送ジョブなら失敗し始めた最初のジョブの時刻）の前後の
  障害報告・仕様変更の告知・アップデート・メンテナンス告知を確認する。

### 7. 打ち手を判定する

`job-failure-triage.md` に従い、打ち手を **設定修正 / 問い合わせ / リトライ** に分類する。

- 根拠（どのログ行・実行履歴・記事から判断したか）を必ず添える。
- 確度が割れるときは複数を確度順に並べ、**どの観察で切り分けられるか**を書く。
- リトライを勧めるときは、書き込みモードから**再実行してよいか**を判断して添える。モードは定義の詳細を GET して確認する。
- 問い合わせを勧めるときは、問い合わせ文面の下書きを付ける。「TROCCO が悪い」と断定せず「疑い」として示す。

### 8. 報告する

次の構成で、短くまとめる。

1. **概要**: ジョブ URL・ジョブ種別・ID、ステータス、実行契機、開始/終了時刻と所要時間、件数
2. **何が起きたか**: 失敗した処理段階と、根本原因と判断したエラー。根拠となるログ行を数行だけ引用する
   （伏せ字済みの行を行番号付きで。許可を得て見た値は、報告に必要な最小限にとどめる）
3. **打ち手**: 設定修正 / 問い合わせ / リトライ のどれか（割れるときは確度順に複数）と、その根拠
   - 設定修正: 定義の現況（手順 5）を踏まえ、どの画面のどの項目を**今の値から何に**変えるか。
     接続先で誰が何をするか（権限付与・IP 許可・再認証など）
   - 問い合わせ: 問い合わせ文面の下書き（ジョブ ID・日時・ログの根拠行・試したこと）
   - リトライ: いつ再実行するか、再実行して安全か（書き込みモード）、繰り返すときの恒久対処
4. **参考**: 参考にしたヘルプセンター記事・障害報告のタイトルと URL（無ければ「該当記事なし」）
5. **補足**: `truncated` による省略、`expired` / `pending`、判断できなかった点

対処に設定変更や再実行が含まれても、この skill では実行しない。ユーザーが望めば手順を示すにとどめる。

### 9. 後片付け

調査が終わったら、作業ディレクトリ（`$out`、生データの `.raw/` を含む）と検索結果（`$TMPDIR/trocco_hc`）を
削除してよいかユーザーに確認し、不要なら削除する（`rm -rf "$out"`）。

## 注意

- 伏せ字化は機械的な処理であり、完全ではない。許可リストに偶然一致する語（一般的な英単語と同じ列名など）は残りうる。
  組織のデータ取り扱い方針に沿って使う（詳細は `job-logs.md`「取り扱いの注意」）。
- Claude Code / Codex では、`.raw/` を直接読むコマンドを PreToolUse hook が止める。ただし hook は失敗時に素通りし、
  コマンドを連結すれば避けられてしまうので、hook の有無にかかわらず上の大原則を守る。
- 報告に貼るログは必要最小限にし、ログ全文をチャットに貼らない。
- ヘルプセンターの検索は `trocco-api.sh` ではなく `curl` で直接行う（API キーは不要で、送らない）。
