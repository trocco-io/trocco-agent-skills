# 命名規則の導出・確認・一括修正

定義名（`name`）の命名規則を実データから導出してユーザーと確定し、非準拠のものを一括リネームする。
対象: 転送設定 / データマート / ワークフロー / dbtジョブ設定。

## 大原則: API はラッパー `trocco-api.sh` 経由で呼ぶ

`curl` で直接叩かない。ベース URL と `Authorization` ヘッダーはラッパーが所有するので、
**パス以降と curl 引数だけ**を渡す（API キーの値を読む必要はない）。

ラッパーの置き場所は導入方法によって変わる。まず次でパスを確定する。

```bash
# ls はエイリアス（-F 等）で表示が変わることがあるため使わない
for p in {.claude,.agents}/skills/govern-naming/scripts/trocco-api.sh bin/trocco-api.sh; do
  [ -f "$p" ] && echo "$p" && break
done
```

以降この SKILL.md と `references/` に出てくる `trocco-api.sh` は、確定したパスに読み替えて実行する。
コマンドごとにシェルは切り替わるため、変数には入れず毎回フルパスで書く。

```bash
bash .claude/skills/govern-naming/scripts/trocco-api.sh "/job_definitions?limit=200"   # パスは確定した値に置き換える
```

## 前提知識（必ず先に読む）
- [`knowledge/trocco-api.md`](./references/trocco-api.md): 認証・ページング・PATCH の挙動
- [`knowledge/naming-conventions.md`](./references/naming-conventions.md): テンプレ・導出・トークン決定可否・修正フロー

## 手順

### 1. 前提・対象選択（読み取り）
`BASE=https://trocco.io/api`、`AUTH`、`jq` を確認。対象種別（既定 4 種すべて）をユーザーに確認。

### 2. 名前の列挙（index のみ・GET）
4 種の index を全ページ取得（`{items,next_cursor}`・空配列キー省略に注意）。
転送は `input_option_type`/`output_option_type`、dbt は `adapter_type` も取得。

### 3. 命名規則の導出（分析）
区切り文字・セグメント数分布・先頭/2番目トークンの頻度から **env 語彙候補**（prod/stg/dev 等）と
**PJ 候補**を提示。転送は末尾2トークンが実コネクタ種別（API）と一致するか検証。
叩き台テンプレート（[`naming-conventions.md`](./references/naming-conventions.md)）と突き合わせ、
種別ごとの推奨テンプレート＋語彙を提示する。

> [!NOTE]
> **既存から規則が導出できないことは普通にある**（実測: 先頭トークンが `test`/`tmp`/`example`/個人名 で
> 分散し、env/PJ の語彙が形成されていないアカウント）。その場合は「導出できません」で止めず、
> **叩き台のテンプレートを提示して合意形成に進む**:
> 1. 「既存名から共通の env/PJ 語彙は検出できませんでした」と率直に伝える
> 2. 既定テンプレート（下記）と、既存名に頻出するトークンの一覧を提示する
> 3. env / PJ の語彙をユーザーに決めてもらう（例: `prod`/`stg`/`dev`、PJ 名の一覧）
> 4. 決まった語彙で改めて準拠/非準拠を判定する
>
> 併せて「**既存の命名を変えない**（規則は今後の新規作成のみに適用）」という選択肢も提示する。

### 4. 規則の確認（ユーザー承認）
導出したテンプレート / env・PJ 語彙 / 区切りを提示し、編集・承認を得て**確定**する。

> [!NOTE]
> **レートリミットに注意**（10 分あたり トライアル 100 回 / Advanced 以上 3,500 回）。
> この skill は対象 1 件につき detail を 1 回取得するため、対象が多いと上限に近づく。
> **実行前に必要回数を見積もり**（一覧 ≒ 全件÷200 回 ＋ detail ≒ 対象件数）、
> 上限に対して大きい場合は対象を絞るかユーザーに確認する。
> ラッパーは 429 を自動リトライする。残量確認:
> `trocco-api.sh '/teams?limit=1' -o /dev/null -D - 2>/dev/null | grep -i x-rate-limit`

### 5. 判定と提案名の生成
各リソースを準拠 / 非準拠に分類。非準拠は提案名を組み立てる:
- **決定可能トークンは自動補完**: 転送コネクタ接尾辞（API `option_type`）、データマート/転送の成果物名
  （detail GET の出力先テーブルが単一・自明な場合）、認識済み env/PJ の正規化。
- **決定不能トークンがある**もの（WF/dbt の成果物名、`query_mode=query`・出力先が式/パス/複数、env・PJ 欠落）は
  **「要ユーザー判断」レポート**へ（部分提案＋不足スロットを明示）。
- **衝突チェック**（提案名どうし / 既存名）と **255 超過**を弾く。

### 6. 提示と適用（変更は要確認）
2 グループで提示:
- (a) **自動修正可**: 完全な before/after を提示 → 承認後 `name` を一括 PATCH（スカラー差分更新）。
- (b) **要判断レポート**: ユーザーが不足トークンを補完 → 必要なら適用。

まず少数で適用 → GET で反映確認 → 横展開。変更した id 一覧を報告。

## やってはいけないこと
- 決定不能な成果物名を**推測で確定・自動リネームしない**（レポートに回す）。
- ユーザー承認前に PATCH しない。提案名の**衝突・255 文字超過**を無視しない。
- 転送のコネクタ接尾辞は**名前から推測せず API の `option_type` を正**とする。
- 大量リネーム時はレート制限に配慮（429 はバックオフ）。リネームは id 参照を壊さず可逆である旨も伝える。
