# ヘルプセンター・お知らせの探し方

> 2026-10-20 時点の確認に基づく。記事の中身はここに書き写さない。毎回その場で検索して読むこと。

TROCCO のヘルプセンター（https://help.trocco.io/hc/ja ）には、エラーメッセージ別の解説、よくある質問、
障害報告・仕様変更の告知がある。ジョブの失敗原因を調べるときの一次情報として使う。

記事は日々追加・更新される。また、**既存の記事に当てはめようとすると判断が偏る**
（ログに書かれていない原因を、似た記事があるという理由で採用してしまう）。
そのため、記事の要約を手元に持たず、**ログから検索語を作り、その場で検索して読む**。

## 何を探すか

| 場所 | 中身 | 使いどころ |
|---|---|---|
| カテゴリ「エラー」 | エラーメッセージ別の原因と対処。節は「ジョブ実行時」「プレビュー」「接続確認」「その他」 | ログのエラー文字列から原因を探す。プレビュー・接続確認の記事でも、同じ原因はジョブ実行時にも起こる |
| カテゴリ「よくある質問・FAQ」 | 仕様の説明、想定外の挙動（スキップ、件数不一致、データ消失、タイムアウトなど） | ログに例外が出ていない失敗や、成功したが結果がおかしいとき |
| カテゴリ「お知らせ」の節「障害報告」 | TROCCO 側・接続先サービス側の障害 | 失敗時刻と重なる障害が無いか。あれば「リトライ」か「問い合わせ」の根拠 |
| 同「仕様変更の告知」「TROCCO アップデート」「メンテナンス告知」 | 認証方式の廃止、API バージョン変更、機能の変更、メンテナンス期間 | 「以前は動いていたのに急に落ちた」ときに、失敗し始めた時期の前後を見る |
| 公式ドキュメント https://documents.trocco.io | コネクタごとの設定項目・前提条件（接続元 IP、必要な権限など） | 設定修正の具体的な手順を示すとき。`/llms.txt` で索引、ページ URL の末尾に `.md` で本文 |

## ヘルプセンターの API（認証不要）

ヘルプセンターは Zendesk で、公開記事は認証なしの API で検索・取得できる。
**TROCCO API ではないので `trocco-api.sh` は使わず、`curl` で直接呼ぶ**（API キーは送らない）。
レスポンスはファイルに保存して `jq` で読む。

```bash
hc="${TMPDIR:-/tmp}/trocco_hc"; mkdir -p "$hc"

# 検索（locale=ja。category で絞り込める。件数と各記事の id / section_id / title / html_url / updated_at が返る）
curl -sS -G 'https://help.trocco.io/api/v2/help_center/articles/search.json' \
  --data-urlencode 'query=OutOfMemoryError' --data-urlencode 'locale=ja' \
  --data-urlencode 'per_page=10' > "$hc/search.json"
jq -r '"count=\(.count)", (.results[] | "\(.id)\t\(.section_id)\t\(.updated_at[:10])\t\(.title)\t\(.html_url)")' "$hc/search.json"

# 記事本文（HTML）。タグを落として読む
curl -sS 'https://help.trocco.io/api/v2/help_center/ja/articles/<記事ID>.json' > "$hc/article.json"
jq -r '.article | .title, .html_url, .updated_at, (.body | gsub("<[^>]+>"; " "))' "$hc/article.json"

# 節の記事を新しい順に一覧（障害報告などを時系列で見る）
curl -sS 'https://help.trocco.io/api/v2/help_center/ja/sections/<節ID>/articles.json?sort_by=created_at&sort_order=desc&per_page=30' > "$hc/section.json"
jq -r '.articles[] | "\(.created_at[:10])\t\(.title)\t\(.html_url)"' "$hc/section.json"
```

カテゴリと節の ID（変わることがあるので、見つからないときは下の一覧 API で取り直す）:

| 種類 | 名前 | ID |
|---|---|---|
| カテゴリ | エラー | `4772518552606` |
| カテゴリ | よくある質問・FAQ | `4772486675614` |
| カテゴリ | お知らせ | `4772466079262` |
| 節 | ジョブ実行時に発生するエラー | `4773476266782` |
| 節 | 障害報告 | `4802176926238` |
| 節 | 仕様変更の告知 | `4773550935710` |
| 節 | TROCCO アップデート | `4773551013918` |
| 節 | メンテナンス告知 | `4773567166878` |

```bash
curl -sS 'https://help.trocco.io/api/v2/help_center/ja/categories.json?per_page=100' | jq -r '.categories[] | "\(.id)\t\(.name)"'
curl -sS 'https://help.trocco.io/api/v2/help_center/ja/sections.json?per_page=100' | jq -r '.sections[] | "\(.id)\t\(.category_id)\t\(.name)"'
```

検索の絞り込みは `--data-urlencode 'category=<カテゴリID>'`。まず絞らずに検索し、ヒットが多すぎるときに絞る。

## 検索語の作り方

検索はタイトル寄りで、**長い文字列はほぼヒットしない**（ログの 1 行をそのまま入れると 0 件になる）。
短く、記事タイトルに出てきそうな語にする。

1. **ログ中の固有のトークン**を 1 つ取り出す。
   - 例外クラス名（パッケージを除く）: `OutOfMemoryError`, `SocketTimeoutException`, `SchemaConfigException`
   - エラーコード: `ROW_LIMIT_EXCEEDED_ERROR`, `INVALID_LOGIN`, `billingNotEnabled`, `invalid_grant`
   - HTTP ステータスと短い句: `429`, `503`, `401 Unauthorized`, `Read timed out`
   - 特徴的な英語の短い句（2〜5 語）: `Private key is encrypted`, `Too few columns`
2. ヒットしなければ、**コネクタ名＋症状の日本語**に切り替える: `Snowflake 権限`, `BigQuery タイムアウト`, `kintone 重複`。
3. それでも無ければ、症状だけで FAQ を探す: `スキップ`, `件数 一致しない`, `一時テーブル`, `リトライ`。
4. 具体的すぎる語で 0 件なら、**一段一般化**する。例: `LONGBLOB` が 0 件なら `BLOB` や、
   エラー文の定型部分 `Unsupported type` で探す（型名違いの同じ原因の記事が見つかる）。
5. 2〜3 通り試して見つからなければ、それ以上は粘らない（下記「記事が無いとき」）。

> [!CAUTION]
> **検索語にログ中の値を入れない**。検索語は外部サービス（ヘルプセンター）へ送られる。
> ホスト名・ユーザー名・テーブル名・ファイルパス・レコードの値・ID は含めず、
> エラーコードや例外名など**どの顧客でも同じになる文字列**だけを使う。

## 記事の読み方

- **当てはまるかを確かめてから使う**。次がログと一致するかを見る。
  - コネクタと向き（転送元か転送先か）
  - エラー文字列（記事の「エラー」欄に書かれた文言）
  - 発生場面（ジョブ実行時か、プレビュー・接続確認だけで起きるものか）
- 検索は本文にも当たるので、**語を含むだけの無関係な記事**が上位に来ることがある
  （例: `RESOURCE_EXHAUSTED` で、そのエラーと関係ない記事ばかりが返る）。タイトルと「エラー」欄で関係を確かめる。
- 記事は**仮説の材料**であり、結論ではない。ログに根拠が無い原因を、記事があるという理由で採用しない。
- `updated_at` が古い記事は、現在の画面・仕様とずれていることがある。手順を示すときは公式ドキュメントでも確認する。
- 報告では、参考にした記事の**タイトルと URL** を示す。本文を長く貼らない。

### 記事が無いとき

記事が無いことは「珍しい問題」でも「問題ではない」でもない。**ログそのものから判断する**。
例外の連鎖を最後まで追い、接続先が返したメッセージ（HTTP ステータス、DB のエラーコード）を接続先サービスの
公式ドキュメントで確かめる。判断がつかなければ、そのとおりに報告する。

## 障害報告・告知と失敗時刻の突き合わせ

「設定は変えていないのに落ちた」「急に落ち始めた」ときは、ログより先にここを見る価値がある。

1. ジョブの `started_at` / `finished_at` を押さえる。転送ジョブなら実行履歴（`/job_definitions/:id/jobs`）から
   **失敗し始めた最初のジョブ**の時刻も押さえる。
2. 「障害報告」を新しい順に取り、その時刻と重なる記事を探す。タイトルにコネクタ名・期間が入っていることが多い。
   `【解消】` が付いた記事は、解消時刻より後に再実行すれば回復が見込める。
3. 失敗し始めた時期の前後の「仕様変更の告知」「TROCCO アップデート」「メンテナンス告知」を見る。
   - 認証方式の廃止・API バージョンの変更など、**利用者側の対応が要る告知** → 設定修正
   - 機能の変更直後から、設定を変えていないのに失敗する → 問い合わせ（副作用の疑い）
   - メンテナンス期間中の失敗 → 終了後にリトライ

打ち手の分類と判断の手掛かりは [`job-failure-triage.md`](./job-failure-triage.md) を参照。
