# 失敗したジョブを探す

> 2026-10-20 時点の公開仕様に基づく要約。齟齬があれば https://documents.trocco.io/apidocs.md を正とする。

期間や定義を指定して、失敗したジョブを洗い出すための知識。
見つけたジョブの原因調査は [`job-logs.md`](./job-logs.md) と [`job-failure-triage.md`](./job-failure-triage.md) で行う。

## API で一覧できるのは転送ジョブだけ

| ジョブ種別 | ジョブの一覧 | 代わりの探し方 |
|---|---|---|
| 転送ジョブ | ✅ `GET /job_definitions/:id/jobs`（**定義ごと**） | |
| データマートジョブ | ✕ | 失敗通知（Slack・メール）に載るジョブ URL、画面のジョブ一覧 |
| dbt ジョブ | ✕ | 同上 |
| ワークフロージョブ | ✕ | 同上。ワークフロー定義のタスクから、配下の**転送設定**は特定できる（下記） |

定義の詳細 API も、直近のジョブやステータスを返さない。データマート・dbt・ワークフローの失敗は API だけでは探せないので、
その旨をユーザーに伝え、ジョブ URL を貰う。

## 転送ジョブの一覧

```bash
# 日時は 'YYYY-MM-DD HH:MM:SS'（空白は %20）。対象はジョブの作成日時。time_zone の既定は Asia/Tokyo
trocco-api.sh "/job_definitions/123/jobs?limit=200&start_time=2026-10-13%2000:00:00&end_time=2026-10-20%2023:59:59&time_zone=Asia/Tokyo"
```

- 返る項目: `id`, `status`, `transfer_record`, `transfer_byte`, `skipped_row_count`, `context_time`, `executor_type`,
  `started_at`, `finished_at`, `created_at`。定義名は返らない（定義一覧から引く）。
- **1 回で返るのは最大 100 件**（公式の上限。`limit=200` を指定しても 100 件で切れる。定義一覧とは違う）。
  `next_cursor` が返る限り続きを取る。**新しい順に返る**ため、続きを取らないと期間の前半を黙って取りこぼす。
- 読むときは `created_at` で並べ替える。
- 失敗として扱うのは `status` が `error` / `timeout`。`canceled` は利用者の中断であることが多いので、既定では分けて数える。

## 呼び出し回数: 定義 1 件につき 1 回

一覧 API は定義ごとなので、**対象の定義数だけ呼び出しが要る**（加えて定義一覧の取得に「全件 ÷ 200」回）。
さらに、期間内のジョブが 100 件を超える定義はページ数だけ増える。**数分おきに実行される定義は、
7 日分でも数十回の呼び出しになる**。期間は短く始め（まず 1〜3 日）、必要に応じて広げる。
定義が数千件あるアカウントでは、全件を見るとレートリミット（10 分あたり 3,500 回、トライアルは 100 回）を超える。
**先に対象の定義を絞り、呼び出し回数を見積もってユーザーに示す**。残量はレスポンスヘッダーで確認できる（trocco-api.md「レートリミット」参照）。

### 対象の定義の絞り方

ユーザーの指定を優先する。指定が無ければ、候補と件数を示して選んでもらう。

| 絞り方 | 方法 |
|---|---|
| 定義 ID を直接指定 | そのまま使う。最も安い |
| 名前 | `GET /job_definitions?name=<部分一致の文字列>` |
| ワークフロー配下 | `GET /pipeline_definitions/:id` の `tasks[]` のうち `type == "trocco_transfer"` の `trocco_transfer_config.definition_id`。子ワークフロー（`trocco_pipeline`）は辿り直す |
| ラベル・リソースグループ・作成者・コネクタ種別 | 定義一覧の `labels` / `resource_group_id` / `created_by` / `input_option_type` / `output_option_type` で絞る |
| 最近作成・更新された定義 | 定義一覧の `created_at` / `updated_at` |

> [!CAUTION]
> **「スケジュールがある定義」だけに絞ると、ワークフローから実行される定義を取りこぼす**。
> ワークフロー配下の転送設定は、定義側にスケジュールを持たないことが多い。実例では、失敗していた 3 定義のうち
> 2 つがスケジュールを持たない（ワークフローから実行される）定義だった。
> スケジュールで絞るときは、ワークフロー配下の定義も足すか、取りこぼす旨を明示する。
>
> また、**スケジュールの ON/OFF は公開 API では判別できない**（`schedules[]` に有効/無効のフラグが無く、
> OFF のものも同じ形で返る）。スケジュールで絞った対象には止まっている定義も含まれ、その分だけ呼び出しが増える。

## 失敗の出方を分類する

定義ごとに期間内のジョブを時系列に並べ、失敗の出方を見る。打ち手の見当が付き、調べる順番も決まる。

| 出方 | 判断 | 次の一手 |
|---|---|---|
| **作成以来一度も成功していない**（定義の `created_at` 以降のジョブがすべて失敗） | 作成時の設定不備 | 設定修正の可能性が高い。最新の失敗ジョブを調べる |
| **ある時点から毎回失敗**（それ以前は成功） | その時点で何かが変わった（設定・データ・接続先・TROCCO） | **最初に失敗したジョブ**の時刻を押さえ、最新の失敗ジョブを調べる。障害報告・告知もその時刻で見る |
| **散発的に失敗**（前後は成功） | 一時的な原因の可能性 | リトライ寄り。繰り返す頻度が高ければ恒久対処も検討 |
| **直近は成功**（失敗の後に回復） | 回復済み | 優先度は低い。再発の兆候があれば報告 |

- 期間の先頭から毎回失敗している定義は、期間を広げて**最初の失敗と最後の成功**を探す（作成日まで遡れば足りる）。
- 失敗し始めた時刻と、定義の `updated_at` を突き合わせる。直前に更新されていれば、その変更が原因の候補になる。

## 報告の形

定義ごとに 1 行にまとめ、調べる優先順に並べる。

| 列 | 中身 |
|---|---|
| 定義 | 名前と ID |
| 最新の失敗ジョブ | `https://trocco.io/jobs/<id>`（目視確認用） |
| 失敗 / 期間内ジョブ数 | 例: 8 / 8 |
| 出方 | 上の分類 |
| 最初の失敗・最後の成功 | 期間内で見えた範囲。遡った場合はその旨 |
| 実行契機 | `executor_type`（スケジュール / ワークフロー / 手動 / API） |

あわせて、調べた定義数・期間・呼び出し回数と、**一覧できなかったもの**（データマート・dbt・ワークフロー、
対象外にした定義）を必ず書く。
