# 失敗したジョブの打ち手の判定（設定修正 / 問い合わせ / リトライ）

ジョブの失敗原因をログから特定したら、**打ち手**を次の 3 つのどれかに分類して提示する。
原因の説明だけで終わらせず、「次に誰が何をすればよいか」まで落とす。

| 打ち手 | 原因の性質 | 典型 |
|---|---|---|
| **設定修正** | 恒久的。直すまで何度実行しても落ちる | 1-1 ネットワークの許可不備 / 1-2 転送元・転送先サービス側の権限・認証 / 1-3 TROCCO の設定値・データ |
| **問い合わせ** | TROCCO 側の不具合が疑われる | 2-1 機能アップデートの副作用、内部エラー |
| **リトライ** | 一時的。再実行で回復が見込める | 3-1 接続先の一時障害 / 3-2 冪等でない実行による状態不整合 / 3-3 TROCCO の一時的なインフラ不具合 |

エラー文字列ごとの個別の原因は、その場でヘルプセンターを検索して確かめる（[`help-center-search.md`](./help-center-search.md)）。
以下は分類のための手掛かりであり、文字列が一致しただけで決めつけない。

## 1. 設定修正（恒久的な問題）

### 1-1. 転送元・転送先またはネットワークの問題

TROCCO から接続先まで到達できない。

- ログの手掛かり: `Connection refused`, `connect timed out`, `No route to host`, `UnknownHostException`,
  `Communications link failure`, SSH / SSM トンネルの確立失敗, SSL / TLS ハンドシェイクの失敗
- 判断: 毎回同じ箇所（接続の確立時）で落ちる。接続先側でネットワーク・FW・セキュリティグループ・
  踏み台・証明書の変更があった時期から失敗し始めている。
- 打ち手（接続先の管理者に依頼することが多い）:
  - TROCCO の接続元 IP アドレスをセキュリティグループ・FW・許可リストに追加する
    （IP は公式ドキュメント・ヘルプセンターを検索して最新を確認する。ここに書き写さない）
  - 踏み台（SSH / SSM）の設定・鍵・ホストを確認する
  - ホスト名・ポート・TLS 設定を接続情報と照合する
- 注意: `Read timed out` やタイムアウトは「到達できない」とは限らず、3-1 の一時障害や処理量の問題のこともある。
  **接続確立前か後か**で切り分ける（確立後のタイムアウトは 1-1 ではないことが多い）。

### 1-2. 転送元・転送先サービス側の権限・認証

到達はできるが、接続先が拒否している。

- DB / DWH: 接続ユーザーが存在しない・ロックされた、スキーマ・テーブルへの権限不足、ロール・ウェアハウスの指定誤り、
  アカウントの停止、課金の無効化
- SaaS: API キー・アクセストークンの失効・取り消し、OAuth の再認証が必要、認証スコープ不足、
  連携ユーザーの退職・権限変更、API の利用上限（日次上限など、時間が経っても戻らないもの）
- ログの手掛かり: HTTP `401` / `403`, `invalid_grant`, `unauthorized`, `access denied`, `permission denied`,
  `insufficient privileges`, `does not exist or not authorized`, `token expired` / `revoked`
- 打ち手: 接続情報の再認証・認証情報の更新、接続先での権限付与。
  **誰の操作が要るか**（TROCCO の接続情報の編集者か、接続先サービスの管理者か）を明示する。
- 認証方式の廃止など、接続先や TROCCO の仕様変更がきっかけのこともある。ヘルプセンターの「仕様変更の告知」を確認する。

### 1-3. TROCCO の設定値・データ起因

上の 2 つに当てはまらない恒久的な失敗。設定や、流れてくるデータの変化が原因。

- カラム定義と実データの不一致（カラムの追加・削除・型の変更）、型変換・日時パースの失敗、
  マージキーの不備、クエリの誤り、存在しないファイル・シート・パスの指定、データ量の増加によるメモリ不足
- 打ち手: 該当する設定画面と項目を示す。データ側の変化（転送元でカラムが増えた等）が原因なら、その旨も示す。

## 2. 問い合わせ（TROCCO 側の不具合の疑い）

### 2-1. TROCCO が原因（機能アップデートの副作用など）

- 判断の手掛かり（**複数揃うほど確度が上がる**）:
  - 設定を変えていないのに、ある時点から失敗し始めた。その直前に TROCCO のアップデート・仕様変更の告知がある
  - ログが TROCCO 内部のエラー（内部 API エラー、システムエラー、TROCCO のプラグイン内部での
    `NullPointerException` など）で終わっていて、接続先のエラーメッセージが無い
  - 再実行しても同じように落ちる（一時障害ではない）
  - ヘルプセンターに「お問い合わせください」と案内されているエラーである
- 打ち手: TROCCO のサポートへ問い合わせる（窓口はヘルプセンターで確認する）。
  **問い合わせ文面の下書き**を用意すると早い。含めるもの:
  - ジョブ種別とジョブ ID（URL）、定義 ID、失敗した日時
  - 失敗し始めた時期と、その前後で設定を変えたかどうか
  - 根拠となるログの行（値や個人情報は伏せる）
  - 試したこと（再実行の有無と結果）
- 「TROCCO が悪い」と断定しない。判断の根拠を添えて「疑い」として示す。

## 3. リトライ（一時的な原因）

### 3-1. 転送元・転送先サービスの一時的な障害

- ログの手掛かり: HTTP `429` / `5xx`, `rate limit`, `too many requests`, `Quota exceeded` / `RESOURCE_EXHAUSTED`（分あたりの上限）, `SERVICE_UNAVAILABLE`,
  `INTERNAL_SERVER_ERROR`, 接続確立後の `Read timed out`, 接続のリセット
- 判断: 直前・直後のジョブは成功している（転送ジョブなら実行履歴で確認できる）。接続先サービスの障害情報・
  ヘルプセンターの「障害報告」で、その時間帯の障害が確認できる。
- 打ち手: 時間を置いて再実行する。**繰り返すなら設定側の対処を併記する**:
  レート制限なら実行時刻をずらす・同時実行を減らす・取得範囲を分割する、タイムアウトなら取得範囲を絞る など。
- 何度再実行しても同じなら一時的ではない。1-2（日次上限・権限）や 1-3（データ量）を疑い直す。
- 取得件数が日々増えている定義のレート制限は、今回は再実行で通っても**再発しやすい**。件数の推移（実行履歴の `transfer_record`）を添える。

### 3-2. 冪等でない実行による状態不整合

前回の失敗・中断・同時実行で転送先が中途半端な状態になり、それが原因で落ちる。または再実行で重複が生じうる。

- ログの手掛かり: 重複キー（`duplicate key`, `DUPLICATES_VALUE` など）、`already exists`、ロック待ち・デッドロック、
  前回の一時テーブルの残存
- 打ち手: 状態を整えてから再実行する。整え方（重複の削除、残った一時テーブルの削除、同時実行の停止）を示す。
- **再実行の前に、書き込みモードで安全性を判断する**（下記「再実行してよいか」）。

### 3-3. TROCCO の一時的なインフラ不具合

- 判断の手掛かり: ログがほとんど出ていない・途中で途切れている、`queued` / `setting_up` のまま長く進まなかった、
  実行基盤（コンテナ・ワーカー）に関するメッセージで終わっている、同時刻に複数の定義がまとめて失敗している、
  ヘルプセンターの「障害報告」「メンテナンス告知」に該当する時間帯の記事がある
- 打ち手: 障害の解消後（記事に `【解消】` が付いた後）に再実行する。
  再実行しても落ちる、または該当する障害報告が無いまま繰り返すなら 2-1（問い合わせ）に切り替える。

## 再実行してよいか（冪等性の確認）

リトライを勧めるときは、**再実行で転送先のデータが壊れないか**を書き込みモードから判断して添える。

| 書き込みモード（例） | 再実行の安全性 |
|---|---|
| 洗い替え（`replace` / `truncate_insert` / データマートの `truncate`） | 毎回作り直すので、再実行してよい |
| マージ（`merge` / データマートの `incremental`） | キーで突き合わせるので、基本的に再実行してよい（キーが一意であることが前提） |
| 追記（`append` / `insert` / データマートの `append`） | 前回分が書き込まれていれば**重複する**。失敗したジョブが書き込みまで進んだかを転送先の件数で確認してから |
| 直接書き込み（`append_direct` / `insert_direct` / `merge_direct` など `_direct` 付き） | 一時テーブルを経由しないため、**途中まで書き込まれている**ことがある。転送先を確認・修復してから |

- スタックトレースに `EmbulkRunner.preview` があるなど、**転送前の段階で落ちている**ジョブは転送先に何も書いていない。
- 転送元が HTTP・HTTPS の `POST` / `PUT` などの定義は、**転送元のサービス側**に書き込んでいる。転送先のモードに関係なく、
  再実行で相手先に二重登録が起きうる（[`job-definition-context.md`](./job-definition-context.md)「副作用のある転送元」）。

- モードは定義の詳細（転送設定の `output_option`、データマートの `write_disposition`）で確認できる。
  モードの詳細は [`incremental-transfer.md`](./incremental-transfer.md)・[`datamart-write-modes.md`](./datamart-write-modes.md) を参照。
- カスタム変数（時刻・日付）で取得範囲を決めている定義は、**再実行時の展開値**が元のジョブと同じになるかを確認する。
  元の `context_time` と異なる範囲を取ると、欠損や重複になる。
- ワークフローのリトライ・再実行の範囲（全体か、失敗したタスクからか）は設定や実行方法で変わる。
  ヘルプセンターで確認してから案内する。
- この判断に必要な情報が取れないときは、「再実行前に転送先の状態を確認すること」を明記する。

## 判定の進め方

1. ログで**最後に起きた根本のエラー**を特定する（[`job-logs.md`](./job-logs.md)）。
2. エラーが**接続の確立前か後か**、**接続先が返したものか TROCCO 内部のものか**を見る。
3. 転送ジョブなら実行履歴で「いつから」「毎回か散発か」を見る（[`job-search.md`](./job-search.md)「失敗の出方を分類する」）。
   散発ならリトライ寄り、ある時点から毎回なら設定修正か問い合わせ寄り、**作成以来一度も成功していない**なら作成時の設定不備（設定修正）。
4. 定義の現況を取得し、ログのエラーと突き合わせる（[`job-definition-context.md`](./job-definition-context.md)）。
5. ヘルプセンターでエラー文字列を検索し、失敗時刻の前後の障害報告・告知を確認する（[`help-center-search.md`](./help-center-search.md)）。
6. 分類と打ち手を決める。迷うときは複数の打ち手を確度の順に並べ、**どの観察で切り分けられるか**を書く
   （例:「1 時間後に再実行して成功すれば 3-1、同じエラーなら 1-2」）。
